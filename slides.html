BACKUPWhy not FP8?

On an H200, FP8 is the first variant I'd add

It fits on one GPU too

At one byte per weight the 70B is about 71 GB, so it runs on a single H200 with roughly half the card left for KV cache, and Hopper has native FP8 tensor cores, so the matmuls themselves get faster (not only the weight reads).

Red Hat's own numbers point the same way

Red Hat's quantization study (Kurtic et al., ACL 2025, over 500,000 evaluations) found FP8 effectively lossless at every model size, with W8A8 winning continuous-batching serving and W4A16 the most cost-efficient for one-request-at-a-time serving, which is the setup this benchmark measured.

RedHatAI's FP8 build of this exact model keeps 99.9% of the BF16 score on OpenLLM v1.

BACKUPWhy spec decode came in last

Speculative decoding wins or loses on two numbers

tokens per 70B pass = (1 − αk+1) / (1 − α)

α is the chance the 70B accepts a drafted token and k = 5 is how many the 8B drafts. From Leviathan et al., 2023.

Acceptance αTokens per pass
0.51.97
0.72.94
0.94.69

The acceptance rate decides how many tokens each 70B pass is worth. vLLM 0.18's draft model proposes its single most likely token, so at temperature 0.7 the target accepts fewer of them than at temperature 0.

The draft's overhead is five small forward passes in a row for every 70B pass, and in vLLM 0.18 the draft runs at the same TP 2 as the target. With enforce_eager, torch.compile and CUDA graphs are both off, so each of those small passes pays full launch cost across the 8B's 32 layers.

BACKUPTwo more fair questions

"Does this hold for smaller models?"

The shape of the trade-off holds, and the risk goes up as the model gets smaller. In Red Hat's study, INT4 kept 97.4% of the 70B's score on the harder OpenLLM v2 suite and 96.1% of the 8B's.

If you're quantizing an 8B, run your eval before you trust it.

"Can you route each request to the right variant?"

Yes. Put every variant behind one Gateway and route on the model name, so chat traffic goes to INT4 and the long reasoning jobs go to BF16, all on one cluster.

On OpenShift AI, llm-d's inference scheduler (Gateway API Inference Extension) then picks the replica within each pool, preferring the one that already holds the request's prefix in KV cache.

BACKUPWhere PyTorch fits

"Why AWQ and not torchao?"

Both land in the same place

torchao quantizes models natively in PyTorch, and vLLM 0.18 serves torchao checkpoints directly. LLM Compressor writes AWQ, GPTQ, and FP8 checkpoints that vLLM runs on its mixed-precision kernels (Marlin, or Machete on Hopper), and Red Hat publishes validated models built that way.

What enforce_eager actually turns off

vLLM normally compiles the model with torch.compile and captures CUDA graphs, so a whole decode step replays with almost no CPU launch overhead. In 0.18, enforce_eager turns off both, which hurts most when the model runs many small passes, and speculative decoding does exactly that.
