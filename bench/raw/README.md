# Raw measurements

Everything the dashboard shows is built from these files: the Llama track by `scripts/build_benchmark_file.py`, the Qwen track by `scripts/build_qwen_file.py`.

- `2026-09-29-r1/`: the afternoon run. 5 requests per setup on one prompt through a port-forward from a laptop, plus the first three preset recordings under `captures/`. Kept as `history` in the benchmark file. The raw files don't record the prompt or the client.
- `2026-09-29-r2/`: the evening run, delivered by the laptop that drove the cluster. `sweeps/<SETUP>/` is `vllm bench serve` inside each pod (`c<N>.json` random prompts, `sharegpt-c<N>.json`, `single-t0.json` and `single-t0.7.json` one at a time); `evals/` is `lm_eval` output; `logs/` has each pod's startup log, versions, `nvidia-smi` samples at 64 in flight, and the spec decode counters read before and after each single-stream run; `captures/` are the preset recordings as delivered (`old-kv-prompt/` answers the earlier wording of the KV cache preset); `live/` is the Sep 30 check of the live path against the FP8 deployment; `scripts/` is the capture script as run.

One recording the demo plays is not the r2 file: `quality/SPEC_DECODE/complex_reasoning.json` is the r1 capture of the sheep riddle (the same answer, token for token, at temperature 0), because the r2 recording was the cold first request on that pod (first token 1.13 s, 36.6 tokens/s, against the benchmark's 62.2) and would contradict the numbers beside it. The r1 capture has no timings, so replay paces it at the benchmark's speed and says so. The r2 file stays here as delivered; the Oct 19 re-record replaces both.

- `2026-09-30-qwen-r1/`: the Qwen3.8-27B track, delivered by the laptop that drove the cluster, on vLLM 0.24.0+rhaiv.13 (image digest in `logs/*-image.txt`). `sweeps/<SETUP>/` as above, plus `single-t0-k{1,2,8}.json` for the MTP passes at 1, 2 and 8 speculative tokens (`SPEC_DECODE/single-t0.json` is 4); `evals/` is `lm_eval` output, `gsm8k_cot` (the generic 8-shot task, not `gsm8k_cot_llama`, so the scores aren't comparable with the Llama track's) and `mmlu_pro`, with three GSM8K files for FP8 (the task was rerun; the latest is the score, the others are listed in the benchmark file); `logs/` has each pod's full startup log and grep, its image digest, GPU and Kueue records, the spec decode counters before and after every single-stream run (`spec-metrics-{before,after}-t<T>-k<K>.txt`), the vLLM 0.24 `--help` dumps, the Phase 0 answers (one with a `<think>` block, from before thinking was turned off server-side), and the MIG profiles; `captures/` are the preset recordings for all five setups, `manifests/` the InferenceServices as exported after they were applied, `scripts/` what ran. `INT4_35` is the same INT4 checkpoint on a 35 GB slice. Some setups have two pods' logs: `qwen-fp8-predictor-85858648f7-gvdvc` is the Phase 0 pod without the thinking flag (the measured pod is `5446d888bb-r9nmt`), and the two `qwen-int4-35gb` pods both ran in eager mode. Things to know when reading the sweeps: the random and ShareGPT sweeps of a setup ran side by side for stretches, with the bench client inside the pod, so those points shared one server (the benchmark file's `sweep_runs` lists every run's window and what overlapped it, and the app draws them hollow as lower bounds); `BF16/single-t0.7.json` and `INT4/single-t0.7.json` ran while the MMLU-Pro eval hit the same pod (lm_eval's start time is on the laptop's clock, four hours behind the pods') and no number is taken from them; the `manifests/isvc-qwen-int4-35gb.yaml` export predates the `--enforce-eager` the pod ran with (its `non-default args` line has it); `nvidia-smi` inside a MIG slice reports no utilization, so the slice setups' `*-gpu-util-c64.csv` hold `[N/A]`; the version files of the measured pods hold only the vLLM version, and torch, transformers and the driver come from the Phase 0 FP8 pod's file (same image). The namespace was replaced with `<namespace>` and nothing else was changed.

The setup folders keep the names they were delivered with: `FP16` is the BF16 setup. `summary.json` was written on the laptop and its `results-2/` paths are that laptop's working directory. `notes.txt` was scrubbed of the cluster and node name and nothing else; its open line "GPTQ kernel TBD from startup logs" is answered by the INT4_RH startup log: `Using MacheteLinearKernel for GPTQMarlinLinearMethod`, the same kernel as the AWQ build. The manifests in `kubernetes/models/` match the args in the startup logs.
